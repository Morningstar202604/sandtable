# sandtable 将台 WARGENERALS 系统重构设计

**日期**: 2026-09-03
**目标**: 以军官/推演使用者视角，重构系统让战役推演有沉浸感、可理解、可操作，同时补齐工程质量与功能短板。

---

## 一、现状诊断（Code Review 结论）

### 1.1 核心问题：缺乏战役叙事与用户引导

- **Web UI 是"控制台"而非"战场地图"**：大量旋钮、参数直接暴露，新手面对几十项 tuning 参数无从下手
- **没有战役简报**：推演开始前玩家不知道自己在模拟什么、目标是什么、天气形势如何
- **事件流信息过载**：所有消息平铺在同一个日志区，无层级分类，无关键事件高亮
- **指标只在推演结束后可见**：无实时战况评估
- **场景选择后缺少"战役背景介绍"**：用户点"渡河"或"诺曼底"后，没有任何上下文帮助理解这个场景代表什么战役

### 1.2 代码层面问题

| 级别 | 问题 | 位置 |
|------|------|------|
| P0 | `__init__.py` 版本号为 "0.1.0"，与 pyproject.toml "0.9.7" 不一致 | `src/wargame/__init__.py` |
| P0 | `_weather_effects()` 是空函数（只 `pass`），天气系统形同虚设 | `world.py:552` |
| P1 | `apply_battle()` 直接修改 `sim.world.tuning` 原地写入，无备份恢复机制 | `battlelib.py:295-302` |
| P1 | 测试仅覆盖 rule 模式，LLM 路径零覆盖 | `tests/test_smoke.py` |
| P2 | `test_normandy_scenario` 中增援检查依赖硬编码单位 ID，脆弱 | `test_smoke.py:108` |
| P3 | 多处 `except Exception` 吞掉真实错误，无结构化日志 | 多处 |
| P3 | 没有类型检查配置（无 mypy config），无 linting 规则（ruff/black） | 项目根目录 |

### 1.3 工程质量缺口

- CI 有 pytest，但仅 8 个冒烟测试，覆盖率估计 < 15%
- 无 linting（ruff/flake8）、无格式化（black/isort）、无 mypy 类型检查
- 无压力测试/性能基准测试
- 无 LLM 路径的单元测试（mock LLM 调用）
- 无 replay 回放系统的独立测试

## 二、设计原则

### 2.1 从军官视角出发

**军官用这套系统时，他想要的不是"调参面板"，而是：**
1. "这是什么战役？谁在打？目标是什么？"
2. "现在战况怎么样？哪里在流血？"
3. "我要做什么决策？系统告诉我能做什么。"
4. "推演完了，我学到了什么？"

### 2.2 设计理念

| 原则 | 具体做法 |
|------|---------|
| **叙事驱动** | 每个场景有战役简报（CINEMATIC BRIEFING），推演过程中有战报节点 |
| **渐进式复杂度** | 默认隐藏高级参数，关键参数才展示，提供"简单/标准/专家"三种模式 |
| **军事术语统一** | 所有 UI 文本使用标准军语，不用技术黑话（如"tuning"->"战役参数"） |
| **实时反馈** | 推演中随时可查看战况，不要等到结束 |
| **可重复验证** | 保持确定性引擎，所有改进不影响可复现性 |

### 阶段二：战役简报系统（用户体验核心）

**目标**：用户进入推演前知道自己在模拟什么

| # | 任务 | 说明 |
|---|------|------|
| 2.1 | 场景元数据扩展 | 为每个场景（cross_river, normandy）添加战役背景文本、双方兵力对比、地形特点、历史参考 |

### 阶段三：UI/UX 重构（"不像推演"的核心问题）

**目标**：让界面看起来像军事指挥系统，而非调参面板

| # | 任务 | 说明 |
|---|------|------|
| 3.1 | 默认"简洁模式" | 折叠高级参数（疲劳/士气/经验等九大战场因素详细参数），只显示核心旋钮（战斗强度、机动、后勤） |
| 3.2 | 添加"模式切换" | 简单/标准/专家三档，专家模式展开所有参数 |
| 3.3 | 事件流分级展示 | 战斗事件/通信事件/环境事件/导演注入 四类分开显示，可折叠 |
| 3.4 | 关键事件高亮 | 重大战果（单位被歼灭/目标易手/天气突变）用醒目颜色标注 |
| 3.5 | 实时战况面板 | 推演中显示各阵营存活单位数、平均战力、补给状态、目标控制权 -- 不要等到结束后才看 |
| 3.6 | 推演结束复盘界面 | 独立复盘视图，显示完整指标、决策 trace 筛选、地图终态 |

### 阶段四：新战役场景--斯大林格勒

**目标**：基于现有引擎能力，设计一个有叙事深度的新场景

**为什么选斯大林格勒**：
1. 城市巷战最能体现"九大战场因素"的价值（工事、经验、士气、伪装、指挥控制）
2. 与现有诺曼底（两栖）、渡河（机动战）形成场景矩阵覆盖
3. 城市地形天然产生 chokepoint，适合多指挥官协作推演
4. 苏德双方兵力悬殊，适合体验"任务式指挥"在不对称作战中的应用

**场景规格**：
- 地图：20x14（中等规模，城市密集）
- 双方：sov（苏军，防御+反击）vs ger（德军，进攻+突破）
- 地形：城市网格（大部分格子为"urban"，道路/伏尔加河作为机动走廊）
- 战役目标：夺占/守住"马雅科夫斯基火车站"（坐标中心区域，高价值）
- 天气脚本：T0-8 雪暴 -> T8-20 阴天 -> T20+ 晴（与历史推进吻合）
- 增援系统：T10 苏军近卫步兵师、T18 德军第6集团军预备队
- 特殊机制：建筑物格提供额外掩体（entrench 加成更高），城市内机动消耗 +50%

**文件**：`src/wargame/scenarios/stalingrad.py` + `test_smoke.py` 新增测试

### 阶段五：LLM 路径优化

**目标**：让 LLM 决策更可观测、更可靠

| # | 任务 | 说明 |
|---|------|------|
| 5.1 | LLM 决策 trace 增强 | 每次 LLM 调用记录完整 prompt（脱敏）、工具调用结果、最终决策 |
| 5.2 | 重试策略改进 | 当前重试逻辑较简单，增加退避+差异化 prompt（把上次错误信息附上） |
| 5.3 | Rule fallback 粒度提升 | 当前 fallback 是"整个阵营切换规则模式"，改为"只对失败 agent 使用规则，其他仍用 LLM" |
| 5.4 | 添加 LLM 路径单元测试 | mock LLM 返回不同结果，验证主路径/fallback/nudge 三条路径 |

### 阶段六：回放与指标系统

**目标**：推演结束后可复盘、可分析

| # | 任务 | 说明 |
|---|------|------|
| 6.1 | JSONL 回放加载器 | 从 events.jsonl 文件重建推演状态，支持跳帧/快进/逐帧 |
| 6.2 | 指挥官决策时间线 | 按时间线展示每个职位的决策内容，可追溯意图->命令->执行链条 |
| 6.3 | 战役指标可视化 | 战力曲线图、补给消耗图、目标控制变化时序图（前端 Canvas 绘制） |
| 6.4 | 导出复盘报告 | 生成 Markdown 格式的战役复盘，包含关键事件、决策摘要、指标统计 |

- [ ] 版本号 `__init__.py` 与 `pyproject.toml` 一致

- [ ] 选择场景后先看到战役简报，再进入推演界面
- [ ] 推演中可实时看到各阵营战况摘要
- [ ] 事件流按类别分类显示
- [ ] 简单模式下核心参数不超过 8 个旋钮

### 新功能
- [ ] 斯大林格勒场景可正常运行，有完整战役背景
- [ ] 推演中每 5 拍产出一条战报
- [ ] 推演结束后可加载回放

### LLM 路径
- [ ] 至少 3 个 LLM 路径测试用例
- [ ] fallback 日志可追踪是哪条路径生效

## 五、风险提示

1. **UI 改动影响面大**：前端 app.js 有 3000+ 行，建议分步替换而非全量重写
2. **LLM 测试依赖外部服务**：mock LLM 时需要精心设计接口
3. **斯大林格勒场景复杂度**：城市地形网格需要额外定义 terrain cost，避免过于困难

---

## 六、实施顺序建议

```
阶段一（工程修复）-> 阶段二（简报系统）-> 阶段三（UI 重构）
                                      ↓
                          阶段四（新场景）<-- 并行开发
                                      ↓
                          阶段五（LLM 优化）-> 阶段六（回放/指标）
```

阶段四可与阶段二/三并行，因为新场景只需要后端场景定义，前端简报系统可复用。
